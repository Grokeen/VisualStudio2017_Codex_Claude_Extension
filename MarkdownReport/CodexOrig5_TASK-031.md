## 1. 사용자 확대를 위한 결론

가장 설득력 있는 초기 고객은 **Visual Studio 2017·2019를 유지해야 하면서 Codex·Claude를 프로젝트 안에서 사용하고 싶은 .NET·C++ 유지보수 개발자와 팀**이다. 기존 IDE·빌드 도구·형상관리를 유지한 채 오류 설명 → 수정 검토 → 적용 → 빌드 확인을 끝내는 경험을 제품의 중심으로 삼는 것이 좋다. VS2022 사용자는 같은 흐름에서 실제 이점이 있는지 별도로 검증한다.

출시의 가장 큰 공백은 새 기능의 수보다 **배포 버전과 설명의 일치, 설치·인증 실패의 해결, 실제 Claude 사용 확인, 프로젝트 문맥의 정확성**이다. 동적 모델 조회·첨부·작업 진행·수정 비교·테마·Markdown 작성기는 이미 구현됐으므로 신규 개발로 다시 제안하지 않는다.

권장 순서는 **현재 후보 안정화 → 처음 사용하는 10명의 설치·수정 성공 확인 → 반복 사용에 필요한 IDE 문맥 강화 → 유통·영문 안내 확대**다. 새로운 범용 에디터나 문서 도구로 범위를 넓히기 전에 실제 개발 작업의 성공률을 높인다. 이 방향은 공식 경쟁 자료와 로컬 구현을 비교한 연구자의 판단이며, 시장 점유율·사용자 인터뷰·성능 실측으로 입증된 결과는 아니다.

## 3. 다른 프로그램과의 비교

월 구독 가격만으로 더 저렴하다고 주장하지 않는다. 확장 사용료, AI 계정 또는 API 비용, 팀 관리 비용, 설치·지원 시간을 구분해야 한다. 현재 사용자별 사용량과 지출 자료가 없어 절감액을 산출하지 않았다.

| ID | 우선순위·노력 | 부족한 부분과 사용자 영향 | 제안 및 완료 기준 |

## 7. 사용자를 늘리는 실행안

### 발견과 설치

제품 설명의 첫 문장을 ‘Visual Studio 2017·2019·2022에서 Codex와 Claude로 코드 수정·검토·테스트를 이어 가는 확장’으로 통일하고, 바로 아래에서 VS 버전별 설치 파일과 AI 계정·네이티브 CLI 필요 여부를 보여 주는 것이 좋다. 검색어는 Visual Studio와 VS Code가 혼동되지 않도록 구분한다.

GitHub 배포와 별도로 Visual Studio Marketplace 등록을 검토한다. Marketplace는 IDE 안에서 검색·설치할 수 있고 버전·지원 SKU·태그·상세 소개·획득 보고를 제공한다. 실제 등록 여부·게시자 소유권·현재 설치 수는 이번 연구에서 확인하지 않았다. 공개 등록은 별도 배포 작업이며 이번에는 수행하지 않는다. [Microsoft 공식 게시 안내](https://learn.microsoft.com/en-us/visualstudio/extensibility/walkthrough-publishing-a-visual-studio-extension?view=vs-2022)

소개 자료는 첫 화면에서 ① 버전 선택 ② CLI·공식 로그인 ③ 한 파일 수정과 빌드 성공의 세 흐름을 빠르게 읽게 한다. 합성 예제·설명 도식·실제 계정 실행 캡처는 캡션으로 구분한다. 기존 GIF·PDF는 유지하되 처음 방문한 사용자가 모든 부록을 읽어야 설치할 수 있는 구성은 피한다.

### 첫 성공과 재사용

프레임워크·언어 버전이 고정된 작은 샘플을 제공하고 ‘설명하기’, ‘버그 고치기’, ‘빌드 오류 해결’의 시작 문구를 제공한다. 실제 요청을 보내기 전에 AI 계정의 사용량이 발생함을 알리고, 자동으로 유료 테스트를 실행하지 않는다. 진단은 실제 모델 요청과 구분한다.

사용자가 다음 날 돌아올 이유는 채팅 기록 자체보다 ‘지난 수정과 검사 결과를 확인하고 같은 프로젝트 작업을 이어갈 수 있음’이다. 솔루션별 대화·현재 프로젝트 표시·전달 문맥 요약을 우선하고 새 역할·장식 옵션 증가는 뒤로 둔다.

### 추천과 팀 도입

초기 검증 후 .NET·C++ 유지보수 커뮤니티에 실제 사용 가능한 샘플과 재현 영상을 제공하고, 질문·설치 실패를 지원 문서에 반영한다. 게시·메시지 발송은 별도 사용자 지시가 있을 때 수행한다. 팀에는 단일 담당자·지원 버전·업데이트와 되돌림·오류 진단 절차를 함께 제시한다. 소스가 모두 로컬에만 머무른다거나 CLI 설치만으로 완전한 오프라인 AI가 된다는 표현은 사용하지 않는다.

## 9. 검증 방법과 측정 지표

핵심 지표는 **한 주 동안 자신의 프로젝트에서 AI 변경을 검토·적용하고 빌드 또는 테스트 성공을 확인한 사용자 수**로 제안한다. 다운로드 수와 요청 수만으로 실제 가치를 판정하지 않는다.

| 단계 | 측정할 것 | 개인정보 수집을 최소화하는 방법 |
|---|---|---|
| 발견 | 소개 방문·버전별 다운로드·유입 경로 | 가능한 공개 배포 통계와 자발적 설문. 다운로드를 설치로 간주하지 않음 |
| 연결 | 설치 완료·CLI 발견·계정 확인·첫 응답까지 시간 | 초기에는 동의한 테스터의 관찰 기록. 서비스 ID·비밀번호·토큰 불필요 |
| 작업 | 수정안 승인·적용·빌드/테스트 성공과 실패 이유 | 내용 대신 단계·결과·환경 버전. 중지·오류는 성공과 분리 |
| 유지 | 7일·28일 뒤 실제 프로젝트 재사용 | 동의한 테스터 재확인. 서로 다른 코호트·분모를 분리 |
| 지원 | 설치 실패율·문제 해결 시간·반복 장애 | 경로·계정·연결 문자열·소스·프롬프트를 제거한 진단 |

기본 원격 수집기를 이번 연구에서 추가하지 않는다. 자동 측정이 필요해지면 사용자가 확인할 수 있는 선택형 수집·삭제·보존 정책을 먼저 마련한다. 최초 관찰만으로도 설치의 어느 단계에서 포기하는지는 확인할 수 있다.

### 첫 사용자 조사

VS2017·2019 사용자6명과 VS2022 사용자4명을 초기 모집안으로 둔다. .NET과 C++를 함께 포함하되 실제로 구형 IDE를 유지하는 이유를 먼저 확인한다. 물을 내용은 현재 IDE·이동 불가 이유, 기존 AI 도구, 실패하는 작업, 소스 전송 제약, 설치 장애, 주당 사용·유료 도입 조건이다. ‘이 기능이 좋으냐’보다 최근 실제 작업을 재현하게 한다.

경쟁 도구 비교는 동일한 작은 저장소에서 ① 코드 설명 ② 구형 API 제약이 있는 오류 수정 ③ 두 파일 변경 ④ 실패한 빌드의 재수정 ⑤ 취소 후 결과 확인을 수행한다. 지원하지 않는 IDE는 ‘해당 환경 비교 제외’로 기록하고 억지로 최하점을 주지 않는다. 도구·모델·버전·계정·프롬프트·컨텍스트·반복 횟수를 기록하고 해결률·작업시간·수동 수정량·실제 사용량을 비교한다. 이번 보고서에는 이 실험의 실행 결과가 없다.

## 10. CodexOrig에게 전달할 개발 요청

구체적인 범위·재현 근거·완료 조건은 [개발 요청서](CodexOrig5_TASK-031_DevelopmentRequests.md)에 정리했다. 우선 **G01 배포 버전과 안내 일치**를 현재 마감 항목으로 전달하고, **G03 진단·G04 문맥·G05 오류 해결 진입**은 다음 주기의 후보로 요청한다. 현재 후보의 소스 동결·실제 IDE 검사 중에 무조건 기능을 추가하라는 요청은 아니다.

실제 Claude 검증은 시험 가능한 계정 환경이 필요하다. 임의 계정 사용·비밀번호 수집·유료 호출을 연구자가 실행하지 않는다. 운영 DB·TFVC·배포 검증의 기존 미확인도 그대로 남긴다. 연구 제안의 전달과 구현 완료는 별개로 기록한다.

## 11. 문서 검증과 작업 경계

자체 검증은 내부 링크 대상, 표 구조, 필수 비교·우선순위·검증 계획·출처, 고정 후보·참조 소스의 SHA 기록을 확인하는 문서 검사다. 결과는 [검증 JSON](CodexOrig5_TASK-031_Validation.json)에 남긴다. 기존 회귀나 공유 제품 빌드를 재실행하지 않는다.

제품 소스·기존 README·USER_GUIDE·Role·다른 담당자의 보고서는 편집하지 않았다. 자기 연구·요청·검증 문서와 공용 협업·이력·상관 보고에 자기 항목만 추가한다. 다른 작업자 진행 중에는 Role에 따라 GitHub 배포를 수행하지 않는다.
